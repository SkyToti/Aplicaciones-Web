Primero: ¿qué es una pila?

Una pila (en inglés, stack) es una forma de guardar cosas una encima de otra, como una pila de platos: el plato nuevo se pone arriba, y el único que puedes quitar es el de arriba. Si quieres el de hasta abajo, primero tienes que quitar todos los demás. Pruébalo:

OperaciónEn inglésQué hace
ApilarpushPone un elemento nuevo hasta arriba
DesapilarpopQuita el de hasta arriba y te lo da
Ver la cimapeekTe dice cuál está arriba, sin quitarlo
¿Está vacía?isEmptyDa true si no hay nada
LIFO: la palabra que tienes que saberte

Last In, First Out: «el último en entrar es el primero en salir». Es la regla de toda pila. Y sí, la pila es una estructura de datos: la vas a volver a ver en esta materia con más calma.

2

La pila de llamadas

Java lleva el control de los métodos que están corriendo con una pila. Se llama la pila de llamadas (call stack) y funciona así:

1Llamas a un método

Java apila un marco nuevo para esa llamada, encima de todos.

2Solo corre el de arriba

El marco de hasta arriba es el que se ejecuta. Los de abajo están en pausa, esperando.

3El método termina

Su marco se desapila, y el de abajo continúa justo donde se había quedado, con el valor que le devolvieron.

¿Qué es un marco?

Un marco (también se le dice registro de activación, o stack frame) es el espacio que ocupa una llamada mientras dura. Guarda tres cosas:

  • Qué método es y con qué parámetros se llamó: por ejemplo, factorial con n = 3.
  • Sus variables locales: las que se crean dentro del método.
  • En qué punto va, para saber dónde continuar cuando le regrese la llamada que está esperando.
Por esto funciona la recursividad

Cuando factorial(3) llama a factorial(2), se apila un marco nuevo con otra n, que vale 2. La n = 3 sigue intacta en el marco de abajo, esperando. Hay tantas n como llamadas en curso, y ninguna pisa a otra.

4

Ida y vuelta: el truco de «¿qué imprime?»

Una recursión como la del factorial tiene dos momentos. En la ida, las llamadas se apilan hasta llegar al caso base. En la vuelta, se desapilan una por una, de la última a la primera. Por eso importa dónde está cada instrucción respecto a la llamada:

Antes de la llamada → en el orden de las llamadas

public static void f(int n) {
    if (n == 0) return;
    System.out.print(n + " ");
    f(n - 1);
}

f(3) imprime 3 2 1. Cada llamada imprime al bajar, antes de llamar a la siguiente.

Después de la llamada → en orden inverso

public static void f(int n) {
    if (n == 0) return;
    f(n - 1);
    System.out.print(n + " ");
}

f(3) imprime 1 2 3. Cada llamada espera a que terminen las llamadas que hizo, e imprime al regresar. La primera en imprimir es la última que entró.

La regla para el examen

Lo que está antes de la llamada recursiva se ejecuta en el orden de las llamadas. Lo que está después, en orden inverso. Si hay algo antes y algo después, la salida queda en espejo: con un print en cada lado, f(3) imprime 3 2 1 1 2 3.

Velo moverse: en el visualizador de arriba elige Ida y vuelta. Y si eliges Fibonacci, fíjate en algo distinto: como cada llamada hace dos llamadas, la ida y la vuelta se van alternando.

La prueba de escritorio

Así se le llama a seguir un programa a mano, en papel, sin computadora. Es lo que te pueden pedir en un examen escrito. Con recursión hay dos formas de hacerla; usa la que pida tu profe.

Forma 1 · la escalera

factorial(3)
= 3 * factorial(2)
= 3 * 2 * factorial(1)
= 3 * 2 * 1 * factorial(0)
= 3 * 2 * 1 * 1
= 6

Vas reemplazando cada llamada por lo que vale, hasta que ya no queda ninguna.

6

StackOverflowError: cuando la pila se llena

La pila de llamadas no es infinita. Cada llamada pendiente ocupa un marco, y si se acumulan demasiados ya no cabe uno más. Entonces Java detiene el programa con este mensaje:

Exception in thread "main" java.lang.StackOverflowError
	at Main.suma(Main.java:4)
	at Main.suma(Main.java:4)
	at Main.suma(Main.java:4)
	...

Se lee así: «la pila se desbordó, y lo que se estaba repitiendo era el renglón 4 del método suma, llamándose una y otra vez». Suele pasar después de miles de llamadas pendientes; el número exacto depende de la computadora y de cuánto ocupa cada marco.

Las tres causas de siempre

1. No hay caso base

Nada detiene las llamadas.

return n + suma(n - 1);
2. Nunca se llega al caso base

Existe, pero las llamadas no se acercan a él, o se lo brincan.

if (n == 0) return 0;
return n + suma(n + 1);
3. El caso base se revisa tarde

La llamada recursiva está antes del if.

long resto = factorial(n - 1);
if (n == 0) return 1;

Y una cuarta, menos común: la recursión está bien hecha pero el problema es demasiado grande. suma(1000) funciona sin problema, pero con suma(100000) lo normal es que truene aunque el método sea correcto: son cien mil marcos pendientes al mismo tiempo. Ahí conviene un ciclo.
